# 셀핀다가바 TF 운영 보드

기준일: 2026-09-10. 이 보드는 실제 전문가 자격·섭외를 주장하지 않는다. AI 역할은 제작·검토 보조이며 제품 사실·공개 문구와 운영 정책에는 지정 책임자가 필요하다.

## 목표 계약

`내 상태 발견 → GABA를 쉽게 이해 → 발효가바 신뢰 확인 → 제품 선택 → 결과 공유 → 구매`를 구현한다. 상세 연구와 실제 사용 후기의 정보 밀도를 유지한다. 범위와 검증 계약은 `REQUIREMENTS.md`에 둔다. 1차 9기능, 2차 챌린지·회원 기록·추천 보상·AI 및 친구 비교·재방문 콘텐츠를 모두 추적한다.

아래 초기 보드의 pending은 착수 시점 기록이다. 현재 검증 증거와 단계별 한계는 IMPLEMENTATION_STATUS.md 최신 업데이트를 우선한다. 임시 배포를 전체 운영 완료로 바꾸지 않는다.

## 자동 협업 규칙

1. PM이 요구 ID, 목적, 담당, 의존성, 산출물, 완료 조건을 포함한 작업을 배정한다.
2. 병렬로 수행 가능한 문안·근거·UX·서버·프런트 작업은 독립 작업으로 나눈다. 같은 파일 소유권은 겹치지 않게 지정한다.
3. 제안자가 근거와 시안을 제시하고, 다른 역할이 반론을 기록한다. 반론은 문제→사용자 영향→대안→검증 방법으로 작성한다.
4. PM은 구현 선택을 결정하고 제품 사실·공개 승인 권한이 필요한 항목만 지정 책임자에게 연결한다. 미확인 자료가 있어도 독립 작업은 계속한다.
5. 구현 후 테스트·실제 화면·저장 결과를 첨부한다. 승인된 콘텐츠 버전과 배포 버전을 연결한다.
6. 운영자에게 결정사항·실행 미리보기·남은 pending을 보여준다. 존재하지 않는 기능을 시연 완료로 보고하지 않는다.
7. 반복 회의는 별도 스케줄러 설정 전에는 자동 실행 중이라고 주장하지 않는다. 현재 실행 내 협업과 미래의 상시 운영을 구분한다.

작업 상태: `pending → ready → in_progress → review → verified → released`. `blocked`에는 막힌 의존성과 다음 행동을 기록한다. `verified`는 증거 첨부 후, `released`는 운영 URL 재검증 후만 사용한다.

## 회의 결정 기록 양식

`결정 ID / 관련 요구 ID / 논점 / 제안 / 반론 / 자료·실행 증거 / 결정 / 결정자 / 구현 담당 / 재검토 조건 / 상태`

### 초기 결정

- D-01: 제품비교를 맨 앞에 두지 않고 자기 발견과 이해를 앞세운다. 빠른 제품 탐색은 유지한다. 이유: 사용자 목표의 최종 흐름을 우선한다.
- D-02: 일반 GABA 연구·발효 출처·완제품 근거·개인 후기는 유형을 구분한다. 이유: 정보 밀도를 유지하며 적용 범위를 오해하지 않도록 한다.
- D-03: 리듬 체크 결과는 비진단 생활 안내다. 이유: 답변으로 생체 수치·결핍·증상별 용량을 추정할 수 없다.
- D-04: 승인·분석은 서버 영속성을 완료 조건으로 둔다. 이유: 화면 데모와 실제 운영을 구별한다.
- D-05: 구매 클릭과 실제 구매는 별도 지표다. 이유: 외부 판매처 도달만으로 전환을 증명할 수 없다.
- D-06: 2차는 후속 작업이며 삭제·축소하지 않는다. 전체 목표 완료와 1차 공개 완료를 구분한다.

## 후기 운영 TF 후속 결정

마케팅·소비자 심리 역할이 ReviewEditor를, UX·서버 역할이 Node/D1 승인 API를, 주 담당이 공개 카드와 실제 API 브라우저 연결을 구현했다. 근거 역할 독립 검토에서 legacy 안내문을 통한 인용 승인 우회가 발견돼 고정 안내문/회귀검사로 수정했다. 단일 운영자 검토 기록이라는 한계를 UI에 표시한다. 실제 후기 없는 상태에서 인용을 만들지 않고 사용권 입력을 기다린다.

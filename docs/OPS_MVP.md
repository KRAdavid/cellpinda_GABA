# 운영 MVP — 공개용 GABA 논문 마스터 인덱스

기준일: 2026-09-11

이 MVP는 한 문장 목표를 `Goal Contract → 목표별 TF → 업무 그래프 → 샌드박스 실행 → 결과·승인 보고`로 바꾼다. 공개 사이트의 실제 연구 데이터는 승인 원장 `data/content-ledger.json`에서 생성되며, 빌드 시 `public/data/gaba-master-index.json`으로 export한다.

## 실행 방법

1. `?view=ops` 화면을 연다.
2. 목표 문장을 입력하고 **Goal Contract 자동 생성**을 누른다. 입력 문장에서 스트레스·수면·성장호르몬·근육·제품·근거 같은 초점을 추출해 계약과 보고서에 남기고, 안전한 내부 업무 파동을 즉시 시작한다.
3. 생성된 목표·성공 기준·중단 조건과 TF 역할을 확인한다. 생성형 TF도 `data/tf-role-registry.json`의 6개 필수 역할군을 만족해야 하며, 역할이 빠지면 CI가 배포를 막는다.
4. 자동 파동이 `READY` 업무를 우선순위대로 샌드박스에서 실행한 뒤 `VERIFYING`에서 멈춘다. 담당 검증자가 수락 기준을 모두 확인하고 검토 메모를 남겨야 `DONE`으로 전환되며, 그래프의 파동 버튼은 승인 후 재개하거나 다음 업무를 다시 연다.
5. 외부 약속 위험이 있는 공개 배포 단계는 승인 요청으로 멈춘다. 승인하면 저장된 `WAITING` 작업이 `READY → RUNNING → VERIFYING`으로 재개된다.
6. TF 의사결정 기록에서 참여 역할·판단·반대 의견·다음 조치를 확인한다. 자동 안전 경계와 사람이 회의에서 작성한 반대 의견은 구분되어 표시되며, 작업을 선택하고 10자 이상의 재검토 조건을 입력해 회의 기록을 추가할 수 있다.
7. 결과·감사 로그·승인 상태를 JSON으로 복사하거나 내려받는다.

업무 그래프의 **자동 협업 파동 실행**은 목표 생성 때 자동으로 시작되며, 그래프에서 다시 눌러 다음 업무를 재개할 수 있다. 현재 실행 가능한 내부 업무를 우선순위 순서로 하나씩 실행하고 `VERIFYING`에서 독립 검토자의 판정을 기다린다. 검증자는 카드의 수락 기준을 모두 체크하고 메모를 남겨 승인하거나 보완을 요청한다. 각 단계마다 감사 이벤트와 TF 의사결정을 남기며, 외부 약속 작업에서 자동으로 멈춰 승인 보고서를 만든다. 따라서 한 문장 입력만으로 내부 작업을 이어가면서도 승인 경계를 우회하지 않고, 승인 후에는 같은 그래프에서 다시 이어갈 수 있다.

canonical 업무 그래프의 현재 상태는 `pnpm run tf:pulse`로 다시 읽을 수 있다. 이 파동은 `VERIFYING`·`WAITING` 작업마다 실행 담당·독립 검증자·근거·다음 조치를 자동 제안하고, 대기 작업은 입력이 생기기 전까지 보류한다. 자동 pulse는 사람의 반대 의견을 발명하지 않으며, 출력에 `human-meeting-required`를 남겨 회의에서 보완하게 한다.

전체 목표의 현재 판정은 `pnpm run audit:goal`에서 확인한다. 이 명령은 계약·TF 레지스트리·업무 그래프·샌드박스·공개 인덱스 검증을 함께 실행하고, B2·B3·B4·C2·E1 같은 외부 게이트는 `VERIFYING`·`WAITING`으로 남겨 완료와 구분한다. `--json` 출력은 회의·CI가 읽을 수 있는 상태와 다음 입력만 포함한다.

JSON 감사 출력의 `pulseHealth`는 저장된 heartbeat 시각·상태 지문·경과 분을 포함한다. 8시간을 넘기면 `stale`로 표시해, 운영 보드의 `업데이트 지연`과 같은 기준으로 자동 주기의 지연을 확인한다.

로컬 자료까지 같은 회의 패킷에 연결할 때는 지정 폴더가 있는 PC에서 `pnpm run audit:goal:local`을 실행한다. JSON이 필요하면 `pnpm run audit:goal -- --local-inputs --json`을 사용한다. 이 옵션은 완제품 자료 스캔과 주문 파일 구조 감사를 추가해 `local-material-inputs`와 `local-order-inputs`로 표시하고, 가장 최근 파일 수정 시각을 함께 남긴다. 완제품 후보가 발견되어도 B2 독립 검증을 자동 승인하지 않고, 역사 주문의 1500 수량이 있어도 상태·취소·환불·판매자 계정이 확인되지 않으면 E1을 `WAITING`으로 유지한다. 로컬 파일명·경로·개인 행은 공개 export와 CI artifact에 넣지 않는다.

배포 준비도도 같은 감사에 포함된다. Worker 운영 게이트가 그래프에서 실수로 `DONE`이 되더라도 Cloudflare 필수 Secrets와 산출물이 준비되지 않으면 감사가 오류로 판정하므로, 정적 Pages 공개와 영구 Worker 운영을 서로 바꾸어 기록할 수 없다.

같은 자동 판단의 공개 가능한 요약은 `operations-queue.json`의 각 작업 카드에도 `decision`, `decisionMode`, `nextAction`으로 함께 내보낸다. 상세 회의 패킷은 공개 `data/tf-pulse.json`으로 제공하며, 상태·참여 역할·필요 입력·다음 조치만 포함한다. 공개 화면의 canonical 큐와 아래에서 새로 만드는 브라우저 샌드박스는 서로 다른 실행 컨텍스트로 표시하며, 내부 증거 경로를 노출하지 않고 현재 운영 상태와 다음 조치를 이해할 수 있는 수준만 보여 준다.

운영 화면의 `다음 TF 회의 안건`은 pulse가 `VERIFYING` 또는 `WAITING`으로 남긴 작업만 모아 서로 다른 담당자·검증자·다음 조치를 보여 준다. 입력 대기 작업은 `requiredInputs` 체크리스트도 함께 표시해 담당자가 준비할 자료를 바로 확인할 수 있다. `data/tf-role-registry.json`을 기준으로 pulse가 확인한 6개 역할군도 현재 큐에 함께 표시해 교차 검토 책임이 사라지지 않았는지 중간에 확인할 수 있다. 6시간 pulse는 안전한 heartbeat를 저장해 Pages 배포를 깨우며, 화면은 마지막 생성 시각과 상태 지문을 표시한다. 이 목록은 자동 실행을 대신하지 않으며, 회의 의견 입력 폼에서 사람이 판단을 추가해야 다음 판단 기록으로 남는다.

운영 큐 상단의 `목표 감사 JSON`은 같은 Goal Contract에서 생성한 공개 중간 검토 패킷이다. 6개 역할 커버리지, 상태별 작업 수, 논문 인덱스·1500 제품·TF pulse 마일스톤, `VERIFYING`·`WAITING`·`BACKLOG` 게이트와 필요한 입력을 한 번에 확인할 수 있다. `pnpm run validate:public`와 라이브 smoke가 큐·pulse·감사 패킷의 목표 ID·상태·카운트·게이트 일치를 함께 검사한다.

CI와 로컬 production build는 `pnpm run validate:ops`로 전체 샌드박스 여정을 재생한다. 이 검증은 5개 내부 작업의 독립 검증 단계 시뮬레이션과 공개 배포 승인 작업의 `WAITING → READY → RUNNING → VERIFYING → DONE` 전이를 확인하며, 각 샌드박스 완료 기록에 검증자·수락 기준·검증 당시 증거를 별도 기록한다. 실제 원문 검토·외부 게시·구매는 수행하지 않는다.

공개 데이터는 `pnpm run sync:data` 직후 `pnpm run validate:public`에서 다시 검사한다. 제품은 `gaba1500` 하나이고 스마트스토어 목적지만 허용하며, 750 재유입·비공개 필드 노출·마스터 인덱스와 content export의 provenance 불일치를 build 단계에서 차단한다.

티저는 `data/teaser-manifest.json`의 승인 상태를 따른다. 현재 검토 URL은 비로그인 HTTP 200으로 열리는 84초 HTML 애니메이션이지만, MP4/HLS·전체 자막/대본·포스터·권리·표시사항·CTA가 확인되지 않아 공개 미디어 주소로 승격하지 않았다. `pnpm run validate:teaser`는 공개 소스에 검토 URL이 섞이지 않았는지 빌드에서 차단하며, 필요한 승인 자료가 모두 모이기 전까지 자동 협업 파동은 티저 노출을 `HOLD`로 유지한다.

제품 책임자와 표시 검토자는 `pnpm run audit:materials`로 지정 로컬 자료를 읽기 전용으로 재검색할 수 있다. 매니페스트는 1500 소비자 포장과 1 kg·10 kg 벌크 라벨을 구분하고, 결과는 `tmp/local-material-audit.json`에만 저장한다. 자료가 발견되어도 `VERIFYING` 작업을 사람이 승인하기 전에는 공개 원장·문구를 자동 변경하지 않는다.

마스터 인덱스에는 사용자가 지정한 스트레스·수면·성장호르몬·근육발달 연구 축이 각각 하나 이상 포함되어야 한다. 해당 축의 승인 레코드가 사라지면 공개 build를 중단한다.

Pages 배포 뒤에는 `validate-live-public.mjs`가 공개 URL을 재시도하며 페이지 응답, 1500 단일 제품, 스마트스토어 목적지, 750 제거, 네 연구 축, provenance와 5개 스트림·13개 작업 운영 큐의 현재 상태·중복·필수 필드 일치를 직접 확인한다. 대기 작업 수는 외부 입력이 도착하면 자연스럽게 줄어들 수 있다. `operations-queue.json`은 현재 Goal Contract의 담당·검증·대기 입력만 공개 화면에 제공하고 내부 증거·경로는 포함하지 않는다.

화면은 먼저 Worker·D1의 `/api/ops/runs/:runId`에 세션 스냅샷을 저장하고, API가 없는 GitHub Pages 정적 환경에서는 `localStorage`로 폴백한다. `runKey`는 브라우저가 생성하는 샌드박스 세션 키이며 운영자 인증 토큰이 아니다. 서버 스냅샷은 30일 후 만료되고, 모든 저장은 revision과 감사 행으로 남는다. 목표 생성 시 첫 TF 의사결정이 기록되고, 실행·승인 대기·승인 재개·독립 검증 단계마다 참여 역할·판단 근거·반대 의견·다음 조치가 누적된다. 자동으로 생성된 반대 의견은 `guardrail`, 회의에서 사람이 추가한 의견은 `human-meeting`으로 표시하고 작성 시각을 함께 저장한다. `VERIFYING` 작업은 자동 완료되지 않으며, 검증자가 수락 기준·증거·메모를 직접 기록해야 `independent_review` 완료로 남는다. 따라서 이 기능은 재개 가능한 운영 MVP이며 법적·배포 승인 원장을 대체하지 않는다. JSON 보고서에는 계약 스냅샷, 작업별 수락 기준, 작업별 증거, 샌드박스 기록, 독립 검토 기록, 감사 이벤트와 TF 의사결정 기록이 포함된다.

저장 요청은 현재 서버 revision을 `X-Ops-Revision` 헤더로 함께 보낸다. 다른 탭이나 오래된 화면이 같은 run을 덮으려 하면 서버가 `409`로 거부하고 화면은 자동 덮어쓰기를 멈춘다. 사용자는 새로고침으로 최신 승인·감사 상태를 확인한 뒤 다시 작업한다.

정적 GitHub Pages처럼 Worker API가 없는 호스트에서는 `/api`를 미리 호출하지 않는다. 공개 콘텐츠는 빌드된 JSON, 운영 큐는 정적 export, 샌드박스 상태는 브라우저 `localStorage`를 사용해 콘솔 오류 없이 동작한다. Worker를 같은 출처로 배포하거나 `VITE_API_ORIGIN`을 지정하면 콘텐츠·이벤트·운영 상태 저장 API를 다시 사용한다.

서버 저장·복원 양쪽은 `src/domain/ops-validation.ts`의 공통 경계를 통과한다. 허용 필드·길이·업무 ID·의존성·상태 전환을 확인하고, `DONE`에는 `sandbox_simulation` 검증과 `independent-review` 증거를 요구한다. 승인 요청은 `WAITING` 작업과 연결되어야 하며, 이메일·전화번호·토큰·비공개 원문 경로·권리 증거 같은 값은 저장 전에 거부한다. 기존 브라우저 임시 상태를 서버로 보낼 때도 이 정책을 적용하므로, 화면에 임의 완료나 개인정보가 복원되는 경로를 차단한다.

배포 전에는 `pnpm run preflight:deploy`로 Wrangler 설정, production 산출물, 공개 export 범위와 Cloudflare 필수 Secrets의 존재 여부를 한 번에 확인한다. 검증 workflow도 같은 일반 모드를 실행해 매 push마다 준비도를 기록하고, Secrets가 설정된 Worker 배포 job은 strict 모드로 다시 통과해야 한다. 결과는 비밀값을 출력하지 않고 `READY` 또는 `WAITING`과 누락된 이름만 표시하며, `--strict` 모드에서는 하나라도 준비되지 않으면 실패한다.

## GABA 목표 TF

현재 목표에는 TF 리드·AI 비서실, 연구·제품 근거, 마케팅·소비자심리, 제품·품질, 표시·규제 검토, 데이터·성과, 데이터·판매처 운영, 스토리·UX·프런트, 재무·QA, 품질감사관을 배정한다. 각 역할은 책임 결과와 권한 범위를 갖고, 품질감사관과 재무·QA는 실행 담당과 독립적으로 둔다. 회의는 정기 잡담이 아니라 근거·가정·반대 의견·대안·승인 필요 여부·다음 조치를 기록해야 할 때만 연다.

## 공개 인덱스 계약

`gaba-master-index.json`에는 승인된 `research-*` 레코드만 포함한다. 각 레코드는 질문, 연구 설계, 대상, 표본, 용량, 기간, 비교, 측정 지표, 관찰 결과, 소비자 요약, 생활 연결 문장, 한계, 완제품 적용 범위, 공개 원문, 검토일과 근거 해시를 가진다. 필수 필드·소비자 문장·공개 HTTPS 출처가 없는 자료, 철회·보류 자료는 빌드에서 export하지 않는다.

## 운영 경계

현재 화면은 외부 게시·구매·법적 약속을 실행하지 않는 샌드박스다. 자동화 파동은 산출물을 `VERIFYING`에 남기며, 검증자가 수락 기준과 메모를 입력해야 독립 검토 기록으로 완료할 수 있다. CI의 `validate:ops`는 빠른 회귀 확인을 위해 시뮬레이션 모드를 사용하고, 보고서의 `sandbox_simulation_only`로 실제 원문 검토와 구분한다. 샌드박스 결과와 독립 검토 기록 모두 실제 외부 게시 승인을 대신하지 않으며, 외부 약속에는 별도 책임자 승인이 필요하다. 서버 D1 저장은 재개와 변경 이력 보존을 위한 운영 보조 계층이며 관리자 인증·권한 결정을 대신하지 않는다. 실제 운영 전에는 관리자 인증, 서버 영속 감사 로그, 백업·복구, 책임자 승인 연결이 필요하다.
